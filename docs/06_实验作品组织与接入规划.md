# 实验作品组织与接入规划

状态：动态作品架构已确认，各作品实现与部署分别记录。行业 Demo 集与公开版岛见已完成本地实现，尚未部署；海汽原工程保持外部只读。
更新时间：2026-09-14

## 1. 作品关系

主站目前规划教学与课程作品、静眠森、行业 AI 产品实验室三个主要入口方向。实验室是作品集合，每个 Demo 是其内部子作品，可以包含多个页面。医疗、文旅等行业先作为标签，作品数量确实需要时再增加筛选或行业导航页。

其他工具允许作为与上述入口平级的作品存在，不强制归入实验室。例如 AI 场景诊断与原型生成工作台保持独立作品定位。作品的内容层级不决定 App 或 Vercel Project 数量。

主站展示、作品应用、实验后端分别承担入口与内容、交互体验、模型及业务运行职责。工作台是平级工具，不作为所有行业 Demo 的必经上层入口；作品间可关联介绍，业务逻辑不互相耦合。

### 1.1 视觉与体验分层

Demo 合集入口属于作品集外壳，遵循全站 Apple Design 规范，与首页、Project 000 和 AI 场景工作台共享站点页头、基础配色、排版、控件、材料与动效语言。

2026-09-15 作品级例外：用户要求本轮行业Demo集合与岛见使用 `frontend-design` 从零重做，撤销首轮配色限制。两个页面可使用专属刊物式视觉；集合仍保留个人站身份和返回路径，基础可用性及其他作品不变。此例外以[岛见设计记录](projects/island-travel.md#2026-09-15视觉重新设计)为准，不推广成全站改版。

具体行业 Demo 不采用“无风格”约定，也不强制套用作品集蓝色外观。每个 Demo 根据目标用户、使用环境、行业信任线索和核心任务建立自己的视觉方向；主体可以沉浸到行业产品界面中，同时保留清楚而克制的作品集返回入口。无论视觉如何变化，都继续遵守全站的即时反馈、空间一致性、可控动效、响应式、键盘操作和系统辅助偏好要求。

静眠森是已确认的独立创作世界，可以脱离作品集 Apple 视觉外壳，但仍遵守基础可用性和无障碍要求。详细边界以[全站设计语言与交互基线](../../../00_项目总说明/02_全站设计语言与交互基线.md)和[代码实施规范](04_Apple设计与交互实施规范.md)为准。

## 2. 目录与 URL

下面是目标职责示意，尖括号表示实际作品标识，不是待批量建立的目录。现有目录保持原位；首次开发对应作品时只创建用到的部分。

```text
personal-site/

│   ├── main/
│   │   ├── app/works/demos/page.tsx             # 实验室入口
│   │   ├── app/works/demos/<demo-slug>/         # Demo 页面及必要子页面
│   │   ├── app/works/<tool-slug>/               # 其他平级工具
│   │   ├── app/api/experiments/<work-id>/       # 按实际接口需求设置代理
│   │   ├── components/works/demos/<demo-slug>/
│   │   ├── content/projects/demos/              # 作品索引与网页内容
│   │   ├── styles/projects/demos/
│   │   └── public/projects/demos/<demo-slug>/
│   ├── jingmiansen/                            # 已有独立世界
│   └── <standalone-demo>/                      # 已有独立 H5 接入时按需保留
├── services/
│   ├── jingmiansen-agents/                     # 已有专属服务
│   └── experiment-agents/                      # 实际模型/工具/业务状态需求驱动
│       ├── app.py                              # 部署入口
│       ├── pyproject.toml
│       ├── uv.lock
│       ├── .env.example
│       ├── README.md
│       ├── AGENTS.md
│       ├── src/experiment_agents/
│       │   ├── app.py                          # FastAPI 与按需 AgentOS 装配
│       │   ├── config.py                       # 服务端配置
│       │   ├── registry.py                     # 显式注册实际作品
│       │   └── works/<work_id>/                # 各作品实际需要的实现
│       │       ├── api.py                      # 本作品接口
│       │       ├── schemas.py                  # 本作品数据契约

│       │       ├── prompt.md                   # 模型指令，按需

│       │       └── storage/                    # 状态存取，按需
│       └── tests/
└── docs/projects/<work-id>.md                   # 各作品实现与验收说明
```

实验室 URL 采用 `/works/demos`，Demo 采用 `/works/demos/<demo-slug>`；其他平级工具采用 `/works/<tool-slug>`。不把行业名称写入必经 URL 层级，避免分类调整引起迁址。实际作品使用稳定、唯一的 ID；多个 Agent 可用作品 ID 加用途区分。

上述 Demo 路径可以是主站内体验，也可以是介绍与跳转入口。独立前端的实际地址、资源 base path、API 地址及返回作品集方式在接入时记录，不为保持表面 URL 一致而先建设复杂转发。新工具默认留在 `apps/main`；已有合适的 React + Vite H5 可保留独立前端，不强制迁移。动态交互本身不要求拆 App。

工作台首版采用 `apps/main/app/works/ai-solution-lab/`，规则与 Schema 放在 `apps/main/lib/works/ai-solution-lab/`，其余组件、内容、样式按同名作品目录组织。没有独立运行需求时不新建 `apps/solution-lab`。

其他平级工具的组件、内容、样式和素材按现有作品目录规则放置，不塞进 `demos`。不同作品的前端按实际交互分别实现，不强制共用聊天界面或大型组件库。

研究材料继续放在 `01_资料库/`。首个行业 Demo 岛见已建立 `资料_行业AI产品实验室/`，以 README、局部 AGENTS.md 和子作品目录维护资料；已存在的独立工具资料包保留原位。原始材料不放进服务包或公开素材目录。

## 3. 服务复用边界

实验室内 Demo 和其他实验工具默认共用一个 `experiment-agents` 服务，前端默认留在 `apps/main`。Agent、Team、Workflow、工具和知识库按实际作品需要增加，不预建完整平台。

服务采用 FastAPI + Pydantic，Agno 用于实际需要的智能体能力。结构化诊断、规划可以是显式模型调用流程；班次过滤、金额计算、订单幂等和支付状态机归入作品自己的确定性业务模块。可以共用部署，不强制所有业务包装为 Agent，也不强制把已有外部后端立即合并。

各作品明确 Pydantic/OpenAPI 或 JSON Schema 的契约来源，并在边界执行校验；结构校验与业务规则、权限和状态转换校验分别验证。不提前建立全站 contracts 包或类型生成平台，实际出现跨语言重复维护问题后再引入生成工具。复杂工具可以有自己的模板与组件体系，不推广为全站共享 UI。

浏览器经所属 Web App 的服务端接口访问实验服务。代理显式限定作品和允许的调用，不接受任意上游 URL 或无限制透传 AgentOS 管理接口。模型密钥、服务凭据只保存在服务端。

医疗、文旅等演示作品可共用服务与按需数据库实例。读取、写入和删除限定作品、可信访客及会话范围；提示词、知识、业务状态和工具权限按作品组织。跨请求恢复、并发一致性和持久化均构成存储需求，短期 Mock 订单也可能需要数据库。仅标签页草稿可用内存；本地 JSON 文件不直接作为公网多实例状态存储。记录用途、保留期限和清理方式，Production 与 Preview 数据分开。

公网需要访客隔离时，采用服务端签发并验证的匿名会话等方案，不信任浏览器自报的 `user-a` / `user-b`。无需因此增加账号体系。模拟下单也要明确确认、校验状态并保持幂等；模型不能绕过这些规则直接写交易状态。

静眠森继续保留专属服务和既有数据规则，Project 000 的预设互动保持原有方式。实验服务不自动承接全站账号、计费、模型路由平台或所有未来后端业务。

共用服务的作品共同升级依赖、部署和使用资源。出现真实依赖冲突、不同运行时、长任务或独立发布要求时，再评估单独服务；某个前端需要独立 App 时仍可复用实验服务。

## 4. 首次部署与后续接入

前端延续现有部署方式。首次实验后端部署先依据执行时长、流式响应、并发状态、持久化及进程要求选择函数或常驻服务，再记录平台与限制；若选择 Vercel，Root Directory 为 `services/experiment-agents`，不把该平台作为所有后端的硬性要求。主站配置 `EXPERIMENT_AGENT_URL` 与 `EXPERIMENT_AGENT_TOKEN`；独立 H5 使用明确的服务端接入方案，不把共享服务凭据打包进浏览器。服务配置模型密钥，`DATABASE_URL` 和清理任务按实际状态需求增加。

首次验收覆盖 Production 与 Preview 的服务地址、凭据、端到端调用、超时与错误反馈、基本调用限额；有存储时验证会话范围和清理。部署入口和时限以实际运行测试确定，不直接复制静眠森的模型、60 秒时限和全部 Cron 配置。

后续沿用相同能力的 Demo 通常只需增加作品内容、前端、Agent 注册和验证，再部署代码；无需新建 Vercel Project。新模型厂商、外部 API 或存储可能需要补配置；独立前端 App 仍需自己的部署。一次建立基础配置不等于未来永远零配置。

## 5. 现在预留什么

仅在文档中明确作品 ID、目录职责、URL 规则、实验服务入口和环境变量名称。首次有真实作品时，再建立包含标题、简介、行业标签、入口、封面（如有）和展示状态的最小作品索引；不发布空卡片或不可用入口。

不提前创建空应用、虚构 Demo、占位 Agent、空数据库表、通用工具注册平台、队列、CMS、账号系统或共享设计系统。具体模型、工具、存储、页面布局和接口输入输出在首个作品中确定，再依据真实重复抽取共用逻辑。
